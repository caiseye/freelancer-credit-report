## 무엇을 볼 수 있나요

심사 결과가 갈리는 **9가지 케이스**를 **앱 / 웹** 두 가지 화면으로 확인합니다.
첫 화면에서 케이스와 화면 종류를 고르면 그 조건으로 전체 흐름이 실행됩니다.

**프리랜서 5가지**

| 케이스 | 자료 상태 | 특징 |
|---|---|---|
| 정상 승인 | 지표 양호 | 51개월 무중단 · 이상거래 없음 · DSR 4.4% · 월 46만원 흑자 |
| 이상거래 감지 | 소명 필요 | 고액 현금인출·순환거래·가장입금 위험 3건 · 확인 4건 |
| 소득 하락 | 하락 추세 | 12개월간 소득 −66% · 예측도 우하향 · 월 5.6만원 적자 |
| 이력 부족 | 자료 부족 | 개업 8개월 · 일부 지표 산출 불가 · 예측 구간 ±30% |
| 부채 과다 | 상환부담 과다 | DSR 72.4% · 원리금이 가처분소득의 110.7% |

**배달 라이더 4가지** — 배민커넥트·쿠팡이츠·요기요·땡겨요, 대리운전(카카오T·로지)
정산 API로 소득을 확인한다고 가정합니다.

| 케이스 | 자료 상태 | 특징 |
|---|---|---|
| 우량 라이더 | 지표 양호 | 4개 플랫폼 분산 · 완료율 96% · 34개월 무중단 · CV 9.0% |
| 불안정 라이더 | 지표 불안정 | 완료율 68% · 콜 취소 1,140건 · CV 39.2% · 연체 4건 |
| 겸업 라이더 | 지표 양호 | 주간 배달 + 야간 대리 · 6개 플랫폼 · 월 25.8일 운행 |
| 플랫폼 집중 라이더 | 수입원 집중 | 배민커넥트 88.0% · 운행 지표는 양호하나 정책 변경에 취약 |

라이더는 소득 구조가 다릅니다. 필요경비율이 29~34%로 높고(이륜차 할부·유류·
유상운송보험·정비), 우기와 혹한기에 소득이 오르는 계절성이 있으며, 산재보험
가입 대상(특수형태근로종사자)입니다. 성실도 지표도 배달 완료율·콜 수락률·
사고 이력으로 따로 잡았습니다.

'자료 상태'는 대출 승인 여부가 아니라 제출 자료가 어떤 상태인지를 가리킵니다.

### 리포트 구성

1. 요약 — 자료 상태와 핵심 지표
2. **참고 지표와 한계** — 공개 기준선 대비 위치, 양측 관점, 확인되지 않는 것
3. 소득 분석 — 실적·예측 구간(P10/P50/P90)·수입원 집중도(HHI)
4. 계속근무가능성 — 동종 대비 상대평가와 항목별 배점
5. 근로 성실도 — 6개 축 가중평균 (표본 부족 축은 재정규화)
6. **타행 여신 현황** — 기관별 대출·한도·금리·연체, 신용평점, 카드 한도소진율
7. **소비패턴 · 가처분소득** — 카테고리별 소비, 결제수단, 가처분소득 산출 폭포
8. 이상거래 검사 — 12개 규칙 판정과 사유
9. 상환여력 (DSR) — 원리금 근거와 규제 상한 대비
10. 자료 출처 — 수집 기관과 조회 결과
11. 진본 확인 — 문서 메타·해시·타임스탬프

### 중립 원칙

읽는 쪽이 금융기관이라는 점을 감안해, 어느 한쪽을 대변하지 않도록 구성했습니다.

- **판정하지 않습니다** — 승인/부결을 결론 내지 않고, 지표를 공개 기준선
  (DSR 40%, 변동계수 25% 등)과 나란히 놓아 `기준 이내 / 경계 / 기준 밖`
  위치만 표시합니다. 합격선이 아니라 좌표입니다.
- **양측 관점을 병기합니다** — 같은 수치를 「이용자 관점」과 「금융기관 관점」으로
  나란히 적습니다. 어느 쪽 문장도 상대를 깎지 않습니다.
- **한계를 먼저 밝힙니다** — 예측은 보장이 아니고, 현금 거래는 집계되지 않으며,
  승인·한도·금리는 금융기관의 고유 권한임을 명시합니다.

### 본인 확인

전자서명인증사업자 20곳을 지원합니다 — 간편인증 6(카카오톡·네이버·PASS·토스·
페이코·삼성패스), 금융기관 인증서 7(KB·NH·신한SOL·하나·우리WON·IBK·카카오뱅크),
범용 7(금융인증서·공동인증서·signGATE·CrossCert·Magic·SignKorea·TradeSign).

### 앱과 웹의 차이

- **앱** — 모바일 카드 스택. 근거는 바텀시트로 접어둠
- **웹** — 목차 + 번호 매긴 절 + 표 중심의 문서형. 근거를 전부 펼침

### 제출처

여신을 취급하는 금융기관 31곳을 6개 업권으로 담았습니다 — 시중은행 8, 인터넷은행 3,
지방은행 6, 저축은행 5, 카드·캐피탈 5, 정책금융 4. 목록이 길어지면 고르기가 더
어려워지므로, 주요 제출처를 위에 두고 나머지는 업권 필터 + 격자 타일로 묶은 뒤
스크롤 영역 높이를 고정했습니다.

## 실행

```bash
npm install
npm run dev      # http://localhost:5173
```

주소에 상태가 남습니다. `#/<케이스>/<app|web>/<단계>` 형식이라
`#/fds_alert/web/5` 처럼 직접 열거나 링크로 공유할 수 있습니다.

## 검증

데이터 정합성과 화면 분기를 렌더 단계에서 확인합니다.

```bash
npx esbuild smoke.jsx  --bundle --platform=node --format=cjs --outfile=smoke.built.cjs  --loader:.jsx=jsx
node -e "require('./smoke-setup.cjs'); require('./smoke.built.cjs');"   # 9케이스 × 2모드 × 8화면 = 144건

npx esbuild assert.jsx --bundle --platform=node --format=cjs --outfile=assert.built.cjs --loader:.jsx=jsx
node -e "require('./smoke-setup.cjs'); require('./assert.built.cjs');"  # 분기 · 중립성 · 인증사업자 · 제출처 · 라이더 40건
```

## 배포

```bash
npm run deploy     # 빌드 후 gh-pages 브랜치로 올립니다
```

### 자동 배포로 전환하려면

지금은 수동 배포입니다. `.github/workflows/` 를 push하려면 토큰에 `workflow`
스코프가 필요한데, 그 권한 없이도 배포되도록 `gh-pages` 브랜치 방식을 썼습니다.
push할 때마다 자동 배포되게 하려면:

```bash
gh auth refresh -s workflow
```

인증 후 Actions 워크플로를 추가하고, 저장소 설정에서 Pages 소스를
`GitHub Actions` 로 바꾸면 됩니다.

## 구조

```
src/
  core.js        팔레트 · 숫자 포맷 · 훅
  scenarios.js   5개 케이스 정의 + 파생값 계산(합계·변동계수·HHI·DSR·가처분소득)
  finance.js     타행 여신 · 카드 소비 원천 데이터 (프리랜서)
  riders.js      배달 라이더 4케이스 + 여신·소비 데이터
  review.js      중립 구성 — 기준선 대비 위치 · 양측 관점 · 한계
  idps.js        전자서명인증사업자 20곳
  banks.js       제출 가능 금융기관 31곳 (6개 업권)
  ui.jsx         앱/웹 모드를 아는 UI 프리미티브
  blocks.jsx     앱·웹이 함께 쓰는 분석 블록(가처분소득 폭포·여신표·소비차트)
  screens.jsx    가입 흐름과 모바일 리포트 카드
  webreport.jsx  웹 전용 문서형 리포트
  App.jsx        케이스 선택 화면 · 해시 라우터 · 테스트 바
```

수치는 **계산으로 파생**됩니다. 소득 배열만 바꾸면 변동계수·예측 구간·DSR·
가처분소득이 함께 움직이고, 계속근무가능성 총점은 항목 배점의 합으로만 만들어집니다.
그래서 카드에 보이는 숫자와 상세 근거가 갈라지지 않습니다.
